# 006 — Table sizes 9, 10, 11, 12 (was 8, 10, 12)

## Requirement (user, 2026-10-03)
"Przerób aplikację: stoliki będą 9, 10, 11 lub 12 osobowe."
Plans are now handled for **four** table capacities **9, 10, 11, 12**, all at the same time (always shown, generated and compared together). Capacity 8 is gone.

## Decisions (orchestrator defaults — Architect may flag problems)
- Exactly **four** permanent scenarios, keyed by capacity, ordered 9, 10, 11, 12. Everything that says "three plans" becomes "four".
- ~~Floor of 6 guests per table is unchanged~~ → **Floor raised to 8 guests per table** (user, 2026-10-03), for all capacities 9/10/11/12; still waived for a single-table plan.
- **Existing data must survive** (the live DB holds the real guest list and plans). Migration `00002`:
  - scenarios 10 and 12 keep their rows (ids, tables, assignments, pins) untouched;
  - the old 8-seat scenario row is **converted to capacity 9** (tables of ≤ 8 guests are valid at 9; assignments/pins kept; bump `version`);
  - a new scenario for capacity 11 is inserted (empty plan);
  - the `CHECK (capacity IN (8, 10, 12))` must become `IN (9, 10, 11, 12)`. SQLite cannot alter a CHECK in place and `scenario.id` is referenced with `ON DELETE CASCADE` — a naive drop/recreate of `scenario` would cascade-delete every table/assignment. Architect designs a safe migration (goose is run from the app at startup; keep it Pi-safe) and Backend proves it with a test that migrates a file at v1 **with data** and checks nothing was lost.
  - Down migration should be provided on a best-effort basis (mirror) or documented as irreversible.
- No API shape change except: `Capacity` enum `[9, 10, 11, 12]`, "exactly four" scenarios / proposals, ordering 9, 10, 11, 12. Bump nothing else.

### Risks / notes for the orchestrator
1. **Startup migration on the live DB**: runs before the server listens, on the single pooled connection (`SetMaxOpenConns(1)`), inside one transaction — fine at this size, and a failure rolls back and the container fails to start (old data intact). Take `infra/backup.sh` **before** deploying (Phase C) and compare per-scenario counts of tables/assignments/pins after.
2. **Old capacity 8 on the client**: bookmarked URLs (`/wesele/plany/8` or similar) and a remembered "last plan opened" in `localStorage` may hold 8 → Frontend must fall back to a valid capacity (e.g. 9) instead of erroring; API answers 404 for 8.
3. **Odd seat counts (9, 11)**: round-table seat layout, drop preview and move menu must not assume an even count (§ 8).
4. Proposals computed before the upgrade are stale for plan 9 (version bumped) and have no plan 11 — the SPA bundle is replaced by the same deploy, so this only matters for an open tab: a 404/409 toast, then regenerate.
5. **Floor 8 on existing plans:** after deploy, stored tables of 6–7 guests show `under_floor`, so plans 9/10/12 will likely show "Needs recalculation" — expected; the user regenerates. Data is not changed by this. With ~85–100 guests every capacity is feasible by head count (gaps only below 56 guests at capacity 9, see 03-seating-model).
6. Down migration is lossy for plan 11 (deleted) and may leave a 9-guest table in plan 8 (shown as `over_capacity`).
7. `00001_init.sql` still says "three plans / (8, 10, 12)" — deliberately untouched (an applied migration is history; the current schema is 00001 + 00002).
